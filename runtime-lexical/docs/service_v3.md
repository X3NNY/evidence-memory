# 文本服务 v3：保持排序的性能优化

v2 的部署包和报告保持原样。v3 沿用同一混合排序，不改变 embedding、原文分块、分数或 top_k 前缀语义。原始问答44分保留，没有调用模型 API 或 subagent。

## 改动

- 同一进程内，相同用户的并发冷查询合并建索引。等候者重新读取 SQLite generation；Add 在索引构建时提交，新请求仍能看到新版本。
- 查询结果以用户索引和 generation 隔离，按原始 query 精确复用。每次 Search 仍先核对持久状态；不能绕过鉴权或 generation。
- 相同 query 的并发排序合并执行，缓存完整100条候选，再按 top_k 返回新字典；不同 top_k 不重复排序。缓存只存检索到的原文证据，不生成最终答案。
- LRU 双重限制：每个用户索引最多16条、保守估计4 MiB。超大结果不缓存，失败不缓存，返回字典的调用者修改不会污染缓存。CLI 仍默认最多8个用户索引。
- 读索引锁与 Add 的锁分开。新 Add 正在等待 embedding 时，已提交的旧记忆仍可读；提交后的下一次读使用新 generation。

可用 AML_QUERY_CACHE_ENTRIES 与 AML_QUERY_CACHE_BYTES 配置上限；任意一个为0时关闭结果缓存。结果缓存关闭不影响持久向量复用与用户隔离。

## 固定排序候选未采用

只测试了一个预先固定的候选：对主检索排名和最终段落排名作50/50 RRF，k=20。服务只读取原文和检索信号，未使用金标或题型。

| 指标 | v2默认 | 固定候选 |
|---|---:|---:|
| LoCoMo前10条来源召回 | 69.17% | 68.17% |
| LoCoMo 48k完整记录前缀来源召回 | 93.00% | 93.33% |
| LongMemEval前10条来源召回 | 76.21% | 76.21% |
| LongMemEval前100条来源召回 | 99.47% | 100.00% |

LoCoMo 前10条下降1个百分点，未通过预先约定的两套数据各指标不退步条件，所以没有接入默认服务。这个实验仍是重复使用的开发100题，不能视为盲测或问答提分。

## 验证边界

性能比较使用已冻结 v2 部署源码与 v3 当前源码，在独立 Python 进程中读取相同数据库副本，禁用 provider，BLAS 线程均为1。每题首次查询后连续重试3次，逐条比较内容、ID、分数、时间和顺序。重复查询指标用来衡量缓存效果，不能推算不重复新题的整体吞吐率。

8路冷读的竞争测试人为加入30毫秒构建延迟，强制暴露重复构建；只比较构建和排序次数，不采用该测试的耗时宣称速度。另有写入/读取交错、缓存失效、用户隔离、故障重试与内存上限测试。

正式公网容量、真实 embedding 联调和官方 Smoke / Full 尚未进行。下一步仍应优先完成部署接入。
